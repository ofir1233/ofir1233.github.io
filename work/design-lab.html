01 · The problem

Static mockups couldn't answer the real question

The Lab is a working copy of the product: design decisions get made there, with real interactions and realistic data, not in a slide deck.

Read moreShow less

Hear reads every call, chat and ticket between a contact center's agents and its customers. A static mockup shows one tidy state of that. It couldn't answer the real question: how does this design behave for this customer, with their data, at their scale?

What's in the Lab

  • The product's surfaces in one build, grouped as Main, Intelligence and Operations.
  • A workspace for each demo environment, with the customer's logo next to "Powered by Hear".
  • Version switchers on key screens. This home has one for its briefing, V1 to V5.
  • Three items tagged DEV at the foot of the sidebar: News · Directions, Demos and Storybook.
  • Dark and light themes.

How it started

  1. Feb 2026 · A gallery firstA separate component-gallery site. I stopped after two days.
  2. Mar 2026 · My first versionBuilt from scratch, alone: the chat home, sign-in, first versions of several pages, an in-app Design Inspector, and the design system with its first Storybook stories, connected to an AI API so it answers with real AI responses.
  3. Mar to Jul 2026 · Built out with Claude CodeA Lab shell built from the first one, new pages such as Actions, Signals, Knowledge, AI Tasks and News, and copies of screens to try other designs.
  4. Oct 2026 · TodayDemo environments, switchable versions on five key screens, and a demos engine for prospect demos.

Several designs, one click apart

Key screens in the Lab hold more than one design.

A Version control sits in the screen's own toolbar. One click swaps the design while the environment, the data and the view stay where they are.

Topics · Landscape · Boxes · same screen, same data

The same switcher holds a fourth version, Current.

FaceliftUltra Design Lab · demo data

Facelift to Ultra. Drag the handle. Ultra follows the brand guidelines and goes deeper on UX: spot the key pain point, open an AI chat about it right away to understand the cause, and act on it with suggested signals.

The same control on five screens

The switcher isn't a one-off for Topics. Five key screens carry it:

  • the chat home's briefing: V1 to V5
  • Data: V2 and V3 Facelift
  • Topics: Current, Facelift, Refined and Ultra
  • Agent evaluation: V2, V3, V4 and V4 + Filter
  • the Actions board: V1 and V2

Design choice: the switch sits on the screen it changes, as the same small segmented control each time, so another version is one click away without leaving the screen.

Decision 1 · Where an alternative design sits

Should a new design get its own page, or a switch on the screen?

  • Its own page in the navThe earlier pattern: a copy of the page with its own nav item, such as Data and Data V2.
  • A Version switch on the screenFive key screens now carry the switch on the screen itself. The design changes; the data and the view don't.

Result: each version is seen on the same data, in the same place. The three Topics designs above share one demo environment and one view, and only the design changes.

Decision 2 · Gallery or replica

Should the Lab be a component gallery, or a working copy of the product?

  • A component gallery siteMy first attempt, in February 2026: a separate site with a sign-in and a gallery that showed each component with Preview and Code tabs. I stopped after two days, with two sample components in it.
  • A working replica of HearFrom March 2026, built from scratch: the product with its sign-in, navigation and demo data, where a design is tried as a screen among the screens around it.

Result: a design is judged inside the screen it belongs to, with the data it has to carry, not as a part on its own.

Decision 3 · Where components are documented

Document components in a drawer inside the app, or in Storybook?

  • The in-app Design InspectorI built it first: a floating button opened a drawer with Components, Foundations and Icons tabs. I fixed its crashes, documented new components in it and kept it in sync by hand.
  • StorybookAlso mine. By July 2026 it held 122 stories, including a Pages tier that shows whole screens.

Result: I removed the Inspector and kept Storybook.

04 · Demo environments

One build for design reviews and prospect demos

The Lab holds a demo environment for each customer.

Read moreShow less

Sign-in lists them, and a new one starts from a short form: the company's website, a few sentences about it, and a file.

With the version switches, I can compare designs for different kinds of customers.

Decision 4 · Two modes

Should experiments get a shell of their own?

  • One shell for everythingKeep adding every new page to the one shell of my first version.
  • A Lab shell beside itI built a separate Lab shell from the first one, for every experiment, and kept the first shell as Demo mode, with a smaller set of screens.

Result: one sign-in, two modes. New work lands in the Lab first, and some of it moves on to Demo later. The entry still offers both, with Demo marked "In development".

The engine that plays guided demos in the Lab has its own case study: Demos engine.

05 · How I build it

Prototyping in code, with Claude Code

I build the Lab in React with Claude Code, so a design review looks at a working screen, not a picture of one.

Read moreShow less

I'm a designer with a background in coding. I built the Lab from scratch, alone, and connected it to an AI API so it answers with real AI responses.

Three patterns run through the work.

  1. Duplicate, compare, deleteA new idea gets its own copy of the screen while the original keeps working. Later one of them goes: News V1 was dropped, and V2 became the News tab. Data still keeps two versions side by side.
  2. Real fields, illustrative valuesScreens stay close to what the platform really has. News uses real field and metric names with illustrative values, the Data filter presets point only at columns you can really filter on, and an invented "risk" concept was taken out.
  3. Reuse before inventingNew pages are built from parts that exist. The Settings section uses only existing components, and the Knowledge glossary row reuses the item row from Signals.
