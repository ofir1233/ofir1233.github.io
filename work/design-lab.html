Case study · Hear Design Lab

I test Hear's designs on realistic data, before development

Hear is an AI platform that reads every call, chat and ticket in a contact center. On my own initiative, I rebuilt it in code as Hear Design Lab, so a design is judged on a customer's data and volume, not in a tidy mockup.

For
Anyone reviewing a Hear design: they look at a working screen, not a picture of one.
The problem
A static mockup shows one tidy state. A real screen has to hold up with each customer's data and volume.
What I did
Built the Lab from scratch, alone, with Claude Code: a sign-in, demo companies, and screens that hold more than one design.
Where it stands
Started in Feb 2026. As of Oct 2026 it has demo environments and version switches.

The problem

A mockup shows one tidy state; a real screen has to carry a customer's data

Each contact center brings its own data and volume. A picture of a screen can't show whether a design holds up under that, or what happens on a hover or a click. Trying it in the real product means development first.

What the Lab is

Hear's product, rebuilt in code, with demo companies in place of customers

A demo environment stands in for one kind of customer: its own workspace, people, apps and calls. Northwind is one. The Lab is connected to an AI service, so its AI answers are realistic too.

Testing a design

Two designs of one screen, judged on the same numbers

Topics shows what customers called about and how each topic scored. Its wireframe and its built design run on the same demo data: same topics, same numbers. Only the design changes.

Decisions

Three choices that keep every design inside the screen it belongs to

A gallery of parts, or the whole product?

A component gallery Set aside

My first try, in Feb 2026: a separate site that showed each component in Preview and Code tabs. I stopped after two days, with two sample components.

A working copy of Hear Chosen

The product with its sign-in, navigation and demo data.

Why: I judge a design inside the screen it belongs to, with the data it has to carry. How the parts are documented is in the Design system case.

A new design: its own page, or a switch on the screen?

Its own page Set aside

A copy of the page, with its own item in the navigation, next to the original.

A switch on the screen Chosen

Five key screens carried a version switch on the screen itself.

Why: the design changes while the data and the view stay, so two versions are judged side by side.

Experiments and demos: one space, or two?

One space for everything Set aside

Keep adding every new page to my first version.

Two, behind one sign-in Chosen

A separate space for experiments, built from the first version. The first version stays as the demo, with a smaller set of screens.

Why: new work lands with the experiments first, and only some of it moves on to the demo.

How I build

I build it in React with Claude Code, so a review looks at a working screen

I'm a designer with a background in code. Three habits keep the Lab close to Hear.

  1. Duplicate, compare, deleteA new idea gets its own copy of a screen while the original keeps working. Later, one of them goes.
  2. Real fields, illustrative valuesScreens use Hear's real field and metric names. Filters offer only columns and values the table has. I took out an invented "risk" idea.
  3. Reuse before inventingNew pages are built from parts the Lab already has. Settings uses only existing components.

Where it stands

Started in February 2026. As of October 2026 the Lab has demo environments and version switches, and the demo with its smaller set of screens is still in development. The product screens across this site are shown in it, with demo data.

My part

I started it on my own initiative and built it alone, from scratch, with Claude Code.
