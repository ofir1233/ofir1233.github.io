Case study · Data & Signals

A dense call table that stays easy to slice

The challenge
In Hear, an AI platform for contact centers, one table must show which calls need review, which are high priority and what happened on each.
What I designed
I designed V1 to V3 of the Data table and its AI filter. I also designed Signals, the page for AI or rule-based classifiers that run on calls.
Where it stands
V2 and V3 Facelift both still run in Hear Design Lab, a working replica of Hear. V1 is retired.
Role
Design and build in the Lab, with Claude Code
When
Mar–Oct 2026
Scope

01 · The table

Three slim rows hold all the controls

I gave the table the rest of the screen, and a call opens in a side panel next to it.

Read moreShow less

That keeps the filtered table in view, and the arrow keys step through its calls without closing the panel.

  1. Where you are. The breadcrumb, how many calls are in view and how many are still processing.
  2. Tabs. All calls, Needs review, High priority, Alerts, Done and Agent evaluation slice the same table.
  3. Date range first. It sits ahead of every other filter.
  4. Filter. A plain-language box on top, then a searchable list of fields in groups, starting with Call and Alerts.
  5. Columns. One button, with a count, at the far end of the row.
  6. Search and Upload. Top right, apart from the controls that slice the table.
  7. Version switch. V2 and V3 Facelift, two designs of this page.

Flagged calls

A small warning sign marks a call where an alert fired. Open the call and the side panel names the alert and whether it was marked a false positive.

02 · Three versions

Each version put the filters somewhere new

I didn't redesign Data in place: I duplicated the page, changed the duplicate and kept both.

Read moreShow less
  1. V1 · MarchMy first version: a preset dropdown, filter chips, “Add columns” in the header and a filter popover with an explicit Apply.
  2. V2 · MayA duplicate of V1, “so the existing filter system is preserved.” Filters move into a collapsible strip with a describe-your-query box.
  3. V3 · JuneColumn-first: click a column and its filter editor opens, first floating beside the row, then inline under it. V1 was retired.

Why keep more than one

The Lab's version switch lets one screen hold several designs on the same data. Today Data carries a V2 / V3 Facelift switch, and Signals a V1 / V2 one.

03 · Plan vs. build

Saved views: the plan against the build

Two of the one-page plan's recommendations are in the Lab today, one is partly there and one was reverted.

Read moreShow less

The plan had three UI states, eight decisions and 12 edge cases. Each decision gave options, a recommendation and a reason, and each edge case carried a “Handle v1” or “Punt v2” mark.

Its core idea was a View that saves the filters, the visible columns and their order together.

Decision 1 · Where columns go

Should columns sit inside the filter strip, or in their own modal?

  • Inside the stripThe plan's answer. Columns stack under the filters, collapsed to a count, with one Reset, Save and Apply for both. Built first.
  • A columns modalThe pattern the platform already used, opened from an “Add columns” button. Edits stay a draft and only land on Apply.
  • Column-firstA third model, from June: picking a column is the first step of filtering it. Built as its own page.

Why: reuse won over the plan. Columns went back to a modal “in favor of the existing platform pattern.”

04 · Decisions

Existing patterns won twice

Filters went back to an explicit Apply, and Reports and Signals to a grid like the other data pages.

Read moreShow less

Two habits run through my work on Data: reuse what exists, and build filters only from columns and values the table holds. I replaced Data's own filter strip with the one from the Alerts page, and the column-first presets “reference only real filterable columns + real values.”

Decision 2 · When filters apply

Should a filter apply the moment you click, or wait for Apply?

  • Apply on every changeTried on V1 in June: filters applied by themselves and the Apply button went away.
  • An explicit ApplyThe plan's choice, and what the shared filter from Alerts brought back. Set up the conditions, then run them once.

Why: as the plan put it, toggling an option shouldn't re-run the query on every click.

Decision 3 · Table or list

Should Reports and Signals be a grid or an accordion list?

  • A gridRows read the same way as on the other data pages. In March, Reports moved to a grid to match Signals and Agent evaluation.
  • An accordion listTried on both in May. A collapsed row shows a status dot, name, schedule and toggle, and expands to context, trend, details and actions.

Result: Reports went back to a grid in July, and today Signals opens as a table too.

05 · Signals

Signals that fire on their own

I put an AI or System chip beside a signal's ID, so the list shows how that signal runs.

Read moreShow less

With its Auto switch on, a signal runs by itself, and its status says whether it is Active, Triggered, Paused or in Error. Signals feed the rest of Hear: on the Actions board, a task can come from a signal.

Creating one

  • A name, a folder (or a new one, right from the menu) and the model it runs on.
  • Items, one per field, each with a name, a key, a type and its own description.
  • Saving updates the folder's count.

What changed since July

In July, Signals was an accordion list with status tabs. Now its tabs are folders with counts, and Create signal asks for a folder.

I reused the Signals item row in the Knowledge glossary, so a glossary term and a signal field are edited the same way.
