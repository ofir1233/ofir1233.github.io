Case study · Design system

One set of tokens lets a dense AI product read as one product

Hear is an AI platform for contact centers, with dense screens: call tables, scores, filters and chat side by side. I built the design system that makes them speak one visual language.

For
Whoever builds a screen of Hear. So far, that is me, with Claude Code.
The problem
Dense screens need one set of names for color, surface and state.
What I did
Built the tokens, the shared components and their docs, with Claude Code.
Where it stands
Partly shipped: Hear's live theme and Storybook. In full: Hear Design Lab, my working copy of Hear, built in code.

The problem

One screen mixes figures, tables, charts and chat, and must still read as one

Compliance checks every agent, the people who answer the calls, against the center's rules. Its top strip alone holds headline figures, each measured its own way, and a table header with its own team, count and pass mark. Under it sit a grid of scores, a popover with its own chart and a way into chat. Without shared names for color, surface and state, each part would answer the same questions its own way.

Three layers

Components ask for a role, and the role picks the color

I built the tokens in three layers. A component never names a palette color; it asks for a job, such as body text, and that job has one value behind it.

  1. 1
    PaletteNine colors, each with a name and a stated use: Ink for body text, Glass Gray for outlines, Coral for what needs attention, Hear Blue for the brand.
  2. 2
    RolesWhat components ask for: canvas, card, body text, muted text.
  3. 3
    Component setsTokens for one component: the score scale, tag fills paired with their text, a data-grid theme.

“Always prefer semantic tokens in components.” The rule, as the Colors page in Storybook states it.

Storybook is where the system is documented: each story renders the real component, and by July 2026 it held 122 stories for 32 components.

The finding

Hear Blue fails as text on white, so text uses Deep Blue

Because text and surfaces are named tokens, each pair has one contrast ratio, worked out once instead of screen by screen. One pair failed: the brand's own blue. So the blue has two roles: Hear Blue for the mark, selection and the score scale; Deep Blue for links and small blue text.

Switch the color of the label and the link. Ratios on white, the popover's card.

Deep Blue on white: 5.0:1, above the 4.5:1 that text needs. This is what the Lab uses.

WCAG 2 ratios, computed from the token hex values; text needs at least 4.5:1. On Paper, the canvas behind the cards, Deep Blue is 4.5:1 and Hear Blue 2.6:1. Body text in Ink is 17.8:1 on white.

Proof it holds

Up close, on other screens, each color does only its job

Three crops from other screens of the Lab, enlarged. None of these screens sets a color of its own; each asks for a role.

The key decision

Scores run in one blue, so a dense map stays readable

The Topics screen draws each topic as a box sized by its calls, so many scores show at once. The question was how a score scale should look there.

Red to green Set aside

A different color for each score band. On a dense map the colors compete, and the screen is hard to read.

One blue, in steps Chosen

The deeper the blue, the lower the score.

HigherLower

Why: Coral, green and lilac stay for small marks that each mean one thing. The Topics map and its daily list read in one hue.

Hear Blue to mark, Deep Blue to read.

Partly shipped: I moved the product's colors onto this palette (April 2026), turned its main buttons blue, and set up the product's Storybook with its foundations and first components (June 2026); developers then synced the remaining tokens against it. In the Lab: every screen draws on the full set of tokens since March 2026. My part: the tokens, the shared components and both Storybooks, with Claude Code.
